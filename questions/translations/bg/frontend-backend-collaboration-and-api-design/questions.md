### 1. Как проектирате frontend архитектура, която да сътрудничи с backend екипа и да отговаря на нуждите на React frontend?

Започвам с подравняване на **случаите на използване и нуждите от данни** чрез API договори или OpenAPI спецификации. Подкрепям:

- **REST или GraphQL** в зависимост от сложността
- Последователни структури на ресурси
- Поддръжка за пагинация, филтриране и сортиране

Използваме **Postman/Swagger** за ранни макети и **споделени документи за дизайн на API**. Подчертавам **мислене „от frontend“**: минимализираме претоварването с данни и поддържаме реално време или lazy loading, ако е необходимо.

### 2. Какъв е вашият подход към версионирането на API в React приложение, когато backend се развива?

**Отговор:**

Предпочитам **версиониране по URL** (напр. `/v1/users`) за яснота и кешируемост. В React:

- Енкапсулирам логиката за API в услуги:

```jsx
// api/user.ts
export const fetchUser = () => axios.get("/v2/user");
```

- Използвам **feature flags** или превключватели според средата, за да мигрирам грациозно
- Следя изместването на версиите с интеграционни тестове

<br />

### 3. Как проектирате React frontend, за да се справя с несъгласувани или лошо документирани backend API?

**Отговор:**

За да намалим риска:

- Използвам **TypeScript** с runtime валидатори като `zod` или `io-ts`:

```jsx
const UserSchema = z.object({ id: z.string(), name: z.string() });
```

- Абстрахирам отговорите на API чрез адаптери, за да нормализирам данните:

```jsx
const mapUser = (data) => ({ id: data.user_id, name: data.full_name });
```

- Документирам и маркирам несъответствията за рефакторинг от страна на backend

### 4. Каква е вашата стратегия за оптимизиране на API payload-ите за производителност на React app?

**Отговор:**

- Заявявам само нужните полета (`fields=name,email` или GraphQL selection sets)
- Пагинирам списъците, за да намаля натоварването:

```
axios.get('/users?page=2&limit=10');
```

- Компресирам отговорите (Gzip/Brotli) и кеширам където е възможно
- Използвам **сървърно сортиране/филтриране**, за да избегна клиентския overhead

<br />

### 5. Как интегрирате real-time API (напр. WebSockets, Server-Sent Events) в React app?

**Отговор:**

- Използвам **WebSocket** за двупосочни данни:

```jsx
useEffect(() => {
  const socket = new WebSocket("wss://example.com/socket");
  socket.onmessage = (event) => updateState(JSON.parse(event.data));
}, []);
```

- Използвам context или Zustand за споделяне на актуализации на състоянието
- За SSE: използвам `EventSource`, но при нужда правя fallback към polling
- Изчиствам сокетите при unmount, за да избегна memory leaks

### 6. Какъв е вашият подход към мокването на API по време на разработка на React, когато backend още не е готов?

**Отговор:**

- Използвам **Mock Service Worker (MSW)**, за да прихващам реални `fetch`/`axios`:

```
rest.get('/api/user', (req, res, ctx) => res(ctx.json({ name: 'Test' })));
```

- Оглеждам backend контракта с JSON mock-ове или Swagger
- Превключвам mock режима чрез `NODE_ENV` или dev flag
- Моквам на мрежово ниво, за да тествам интеграцията, а не логиката

<br />

### 7. Как се справяте с rate-limited API в React app, без да влошавате потребителското изживяване?

**Отговор:**

- Имплементирам **експоненциално backoff** или обработка на `Retry-After` header-и
- Подреждам или debounce-вам високочестотни заявки:

```
const debouncedSearch = debounce(fetchSuggestions, 300);
```

- Показвам UI feedback (напр. spinners, retry buttons)
- Кеширам често използвани отговори локално, когато е възможно (напр. `react-query`, SWR)

<br />

### 8. Какъв е вашият процес за отстраняване на проблеми с интеграцията frontend-backend в React app?

**Отговор:**

1. **Проверявам Network таба** (status codes, headers, body)
2. Използвам `console.error` или `error boundaries` за видимост
3. Валидирам типовете на API чрез схеми
4. Логирам и сравнявам frontend заявката с backend очакванията
5. Използвам `Postman` или `curl`, за да изолирам backend проблемите

Сътруднича тясно с backend инженери, идеално в реално време по време на debugging сесии.

### 9. Как защитавате frontend нуждите (напр. пагинация, филтриране) в дискусии за дизайн на backend API?

**Отговор:**

- Давам **потребителски сценарии**, които показват въздействието (напр. бавни зареждания, лош UX)
- Предлагам стандарти като query params `limit`, `offset`, `sort`, `filter`
- Подчертавам **mobile производителност** и **грануларност на данните**
- Използвам споделени API спецификации или примери, за да запълня пропуските

<br />

### 10. Как обучавате frontend екип да работи ефективно с backend инженери в React проект?

**Отговор:**

- Въвеждам **API design-first мислене** (напр. OpenAPI, GraphQL schema-first)
- Дефинирам **ясни договори** и използвам инструменти като MSW за разработка
- Подкрепям съвместни прегледи на API дизайна
- Задавам последователни конвенции (напр. service abstraction, error handling)
- Насърчавам **сътрудничество, основано на емпатия**, като и двете страни участват в демонстрации и retros
