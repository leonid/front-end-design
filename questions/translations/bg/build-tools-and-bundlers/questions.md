### 1. Сравнете Webpack, Vite и ESBuild по отношение на скорост, конфигурация и случаи на употреба. Кой инструмент бихте избрали за React проект и защо?

| Функция | Webpack | Vite | ESBuild |
| ------------- | ----------------------------------------------- | -------------------------------------------------- | ----------------------------------------- |
| **Скорост** | По-бавен (особено при повторни компилации) | Светкавично бърз dev сървър чрез нативни ESM + ESBuild | Най-бърз при пакетиране, с минимален набор от функции |
| **Конфигурация** | Силно конфигурируем, многословен | Минимална конфигурация (разумни стойности по подразбиране) | Лек, но с ограничени плъгини |
| **Случаи на употреба** | Големи, зрели приложения, изискващи дълбока персонализация | Съвременни SPA приложения, за които е важен бърз DX | Инструменти, библиотеки или предварителни пакетиращи инструменти |

**Кой инструмент за React?**

> За съвременни React проекти предпочитам Vite. Той предлага изключително бързо стартиране чрез нативни ESM, интегрира се безпроблемно с React и TypeScript и значително подобрява DX спрямо Webpack. За големи наследени приложения Webpack все още предлага по-богата екосистема от плъгини и по-прецизен контрол.

### 2. Как конфигурирате персонализирана настройка на Webpack за React приложение с TypeScript и предварителна обработка на CSS?

Ще ви трябват:

- `webpack.config.js`
- Babel за преобразуване на JSX/TS
- Loaders за `.tsx`, `.css` и препроцесори

```jsx
// webpack.config.js
module.exports = {
  entry: "./src/index.tsx",
  output: { filename: "bundle.js", path: __dirname + "/dist" },
  resolve: { extensions: [".ts", ".tsx", ".js"] },
  module: {
    rules: [
      { test: /\\.tsx?$/, use: "babel-loader", exclude: /node_modules/ },
      { test: /\\.s?css$/, use: ["style-loader", "css-loader", "sass-loader"] },
    ],
  },
  devServer: { historyApiFallback: true },
};
```

Инсталирайте `babel-loader`, `@babel/preset-react`, `@babel/preset-typescript` и конфигурирайте `.babelrc`.

Тази настройка поддържа React, TypeScript и SCSS и е подходяща за мащабируеми frontend архитектури.

### 3. Какви са предимствата на Vite пред Webpack в съвременен React проект?

- **По-бързо стартиране**: няма пакетиране по време на разработка. Използва нативни ESM и ESBuild за незабавен HMR.
- **Опростена конфигурация**: минимален boilerplate. Плъгинът за React е `@vitejs/plugin-react`.
- **Поддръжка веднага след инсталиране**: JSX, TypeScript, CSS Modules, PostCSS.
- **Компилации за продукционна среда**: използва Rollup под капака за оптимален tree-shaking.

### 4. Как оптимизирате процеса на компилация, за да намалите времето за внедряване в CI/CD pipeline?

- **Активирайте кеширане**:
- Използвайте `webpack.cache` (в паметта или във файловата система).
- Използвайте кеширане в CI (напр. за `node_modules`, `dist`, `turbo`, `vite`).
- **Паралелизация**:
- Използвайте многонишкови loaders (`thread-loader`; Vite го прави по подразбиране).
- Разделете компилациите на по-малки задачи (напр. клиентска и сървърна).
- **Tree-shaking и разделяне на кода**:
- Премахвайте неизползван код.
- Импортирайте динамично маршрути/компоненти.
- **Използвайте леки инструменти**:
- Преминете към **Vite** или **ESBuild** за по-бърза разработка и по-малък изходен пакет.
- **Премахвайте големите зависимости**:
- Одитирайте размера на пакета с `webpack-bundle-analyzer` или `source-map-explorer`.
- **Инкрементални компилации**:
- Инструменти като Nx или Turborepo осигуряват кеширане и компилират отново само променените пакети.

### 5. Опишете случай, когато е трябвало да отстраните проблем, свързан с пакетиращ инструмент, в React приложение.

В предишен проект React приложение, използващо Webpack, започна да извежда грешки по време на изпълнение в продукционна среда, въпреки че работеше в средата за разработка. След разследване установих, че:

- Грешката се дължеше на **tree-shaking на модул със странични ефекти**, който не беше правилно маркиран.
- Библиотека на трета страна имаше страничен ефект при импортиране, който отпадаше в минимизираната компилация.

**Стъпки, които предприех:**

1. Активирах `sideEffects: false` в `package.json` избирателно.
2. Използвах `webpack-bundle-analyzer`, за да визуализирам липсващия модул.
3. Добавих маркери `/*#__PURE__*/` за персонализирани помощни модули, за да подпомогна безопасния tree-shaking.
4. Актуализирах конфигурацията на Webpack, за да осигуря детерминистично разделяне на chunk-овете и генериране на source map за по-лесно отстраняване на проблеми.

**Резултат:** компилацията за продукционна среда стана стабилна, по-малка и по-лесна за отстраняване на проблеми занапред.
