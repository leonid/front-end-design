### 1. Как подхождате към тестването на React компоненти? Какви инструменти или библиотеки използвате (напр. Jest, React Testing Library)?

Фокусирам се върху тестването на **поведението, а не на реализацията**, като използвам:

- **Jest** за модулни и интеграционни тестове (бърз и надежден тестов изпълнител).
- **React Testing Library (RTL)** за тестване на взаимодействия с DOM, което имитира реалното поведение на потребителите.
- **MSW (Mock Service Worker)** за симулиране на API отговори.
- **Cypress или Playwright** за end-to-end (E2E) тестове, които симулират реални взаимодействия с браузъра.

Моят принцип е да тествам компонентите така, както потребителите взаимодействат с тях — чрез щракване, въвеждане на текст и наблюдение на резултатите — вместо да тествам вътрешното им състояние.

### 2. Напишете прост тест за React компонент, който визуализира бутон и увеличава брояч при щракване.

```jsx
// Counter.test.tsx
import { render, screen, fireEvent } from "@testing-library/react";
import Counter from "./Counter";

test("increments count on click", () => {
  render(<Counter />);
  fireEvent.click(screen.getByText(/increment/i));
  expect(screen.getByText(/count: 1/i)).toBeInTheDocument();
});
```

### 3. Каква е разликата между модулното и интеграционното тестване в контекста на React приложенията?

- **Модулно тестване**: Тества един компонент изолирано (напр. логика, визуализиране, потребителски събития).
  _Пример: тестване на манипулатора за щракване на компонент `Button`._
- **Интеграционно тестване**: Тества как няколко компонента работят заедно.
  _Пример: тестване на формуляр, който изпраща данни чрез API и визуализира съобщение за успех._

Модулните тестове са по-бързи и по-фокусирани; интеграционните тестове осигуряват по-голяма увереност за реални работни потоци.

<br />

### 4. Как симулирате API извикване в тест на React компонент?

Използвам **MSW (Mock Service Worker)** за реалистична симулация на API на мрежово ниво.

**Пример:**

```tsx
import { rest } from "msw";
import { setupServer } from "msw/node";

const server = setupServer(
  rest.get("/api/user", (req, res, ctx) => res(ctx.json({ name: "Alice" })))
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

Така тестовете отразяват по-добре поведението на приложението в продукционна среда.

### 5. Как структурирате модулните тестове за React компонент, който зависи от външно API?

Изолирам API логиката от UI компонента и тествам и двете:

1. **Тествам отделно API клиента** (напр. `getUser()`).
2. В теста на компонента:
   - Симулирам API слоя (напр. с MSW или Jest mock).
   - Тествам поведението на UI (напр. индикатор за зареждане, съобщение за грешка, визуализиране на данни).

Това разделение подобрява надеждността и яснотата на тестовете.

### 6. Напишете интеграционен тест с Cypress или Playwright за поток за изпращане на React формуляр.

```tsx
// cypress/e2e/form_spec.cy.js
describe("Contact Form", () => {
  it("submits the form successfully", () => {
    cy.visit("/contact");
    cy.get('input[name="email"]').type("test@example.com");
    cy.get('textarea[name="message"]').type("Hello!");
    cy.intercept("POST", "/api/contact", { statusCode: 200 }).as("submitForm");
    cy.get('button[type="submit"]').click();
    cy.wait("@submitForm");
    cy.contains("Thank you for contacting us").should("be.visible");
  });
});
```

### 7. Как подхождате към end-to-end тестването на React приложение с множество потребителски роли?

Симулирам поведението на потребителите според ролите им (напр. администратор и потребител):

- Използвам **Cypress** или **Playwright**, за да вляза като различни роли чрез UI или програмна настройка на сесията.
- Тествам потоци според ролите:
  - Администратор: достъп до таблото, управление на потребители
  - Потребител: ограничен достъп, блокирани маршрути
- Симулирам отговорите за удостоверяване или използвам предварително подготвени тестови акаунти в тестови среди.
- Организирам тестовите сценарии според ролите (напр. папки `admin/`, `user/`).

### 8. Как гарантирате, че покритието на тестовете остава смислено, а не просто число, което трябва да достигнете?

Фокусирам се върху **стойността на тестването**, а не само върху числата:

- Стремя се към висока **плътност на проверките** — не само „покрити“ редове, а проверени резултати.
- Давам приоритет на **критичните пътища**: изпращане на формуляр, актуализации на състоянието, условно визуализиране.
- Използвам **инструменти за покритие на кода** (напр. `-coverage` в Jest), за да откривам непроверени клонове — след което преценявам дали е оправдано да добавя тест.
- Избягвам прекомерното тестване на детайли от вътрешната реализация (напр. извиквания на `setState`).

Редовните **прегледи на тестовете** и **ръчното осигуряване на качеството (QA)** допринасят за качеството отвъд метриките.
